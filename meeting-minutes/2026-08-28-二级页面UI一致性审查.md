# 会议纪要：二级页面 UI 一致性审查（用户端/师傅端）

- 日期：2026-08-28
- 议题：审查用户端（mobile/user/android）与师傅端（mobile/worker/android）二级页面 UI 布局风格是否与一级页面保持一致视觉标准，杜绝"一个 APP 多套标准"
- 主持人：会议主持人（k3）
- 与会人：沈标（规范基线）、陈端（用户端审查）、林师（师傅端审查）、赵构（组件复用审查）、周险（综合评估）
- 方法：静态代码审查（grep 统计 + 抽查精读 + 基线文件精读），所有结论附 文件:行号 证据

---

## 一、总体结论（主持人裁定）

**不是"一个 APP 多套标准"的失控局面，而是"两端各自主标准成立 + 机制性分叉正在繁殖"。**

- 端内：两端二级页骨架高度收敛（用户端 34 页、师傅端约 30 页统一复用共享 TopBar，无一自造顶栏）；"一级页 Pinned 渐变骨架 / 二级页 TopBar 内容流"的双层结构两端对称成立。
- 端间：两端实为两套设计语言（主色、TopBar 形态等六项硬分裂），属端定位差异，**不做强行统一**，但要求"异端同槽允许异值，同端同槽不允许多值"。
- 真正风险（按周险裁决）：① 绕开令牌/组件零成本、无门禁，分叉按季度繁殖（机制病）；② 双层规则只存在于实现、不存在于文档（约定不成文）；③ RN 登录族第二色板有"合法出生证"，不裁决将成为后来者援引的先例。

## 二、各成员发言要点

### 沈标 · 规范基线
- 两端各自内部自洽，但六项硬分裂：主色 0xFF007AFF vs 0xFF1677FF、TopBar 纯色 48dp vs 渐变、返回键 "‹"20sp vs "<"16sp、字号主流档 13sp 独大 vs 12/13 并列、边距主流 14dp vs 12dp、色板命名 Palette 对象 vs 裸常量。
- 同语言项：bg/panel/line 三值完全相同（0xFFF5F6F8/白/0xFFE8EAED）、圆角主流同为 10dp、均固定浅色、骨架策略同构。
- 建议：端内 Token 单源 + 跨端槽位对齐；数值白名单表（边距 2 档/圆角 4 档/字号 5 档整数 sp）；骨架组件即标准（可 lint）。反对统一两端主色为一个蓝。

### 陈端 · 用户端审查
- 结论：骨架一致性相当好（34 页统一 TopBar/PageScaffold/Palette/EmptyState），"主标准成立、旁支分叉"。
- 【高】RN 登录/注册/找回/实名族自建第二套色板（primary 0xFF086CF5 ≠ 全局 0xFF007AFF，RealNamePage.kt:47-56 等），但有 designs/login-register-states-v2 设计稿背书且已真机验收，收编需设计确认。
- 【高】主提交按钮四种规格并存（M3 默认 44dp / 显式 8dp / RN 自绘 46dp / SubmitButton 44dp，且 RatePage.kt:102 有私有同名 SubmitButton）。
- 【高】PointsPage 升 tab 后残留二级页 TopBar + 死返回键（PointsPage.kt:74，栈深为 1 时 pop 无效）。
- 【中】加载态三套并存；横边距 14/16 双轨；卡片圆角 10/12/16 三档。
- 【低】Auth 系 20sp 独立标题；M3 原生弹层质感割裂。

### 林师 · 师傅端审查（battle 修正后）
- 结论：二级页"守住了顶栏，缺了令牌"。
- 【高】F2 硬编码颜色 60+ 处绕过令牌，重灾区 TicketDetailCards.kt 13 处、DetailActions.kt 9 处、MessagesScreen.kt 7 处（实证 ScanScreen.kt:135 硬编码 0xFFE6F4FF）。
- 【中】F3 圆角 9 种取值 45 处无 Shape token；F4 字号 15 种无 type scale（12sp×38 与 13sp×36 并存）。
- 【中】F1 修正版：双层规则未明文化 + 两端骨架组件重复实现（battle 后由原"高"降级）。
- 【低】F5 边距 12dp 主流但长尾破坏 4dp 网格。

### 赵构 · 组件复用审查
- 结论：骨架未失控（双层结构收敛）；真问题是"同职能组件两端各写一份 + 页面绕开组件自造样式"。
- 【高】用户端无共享按钮组件（28 个 Button 调用点散在 18 文件，ButtonDefaults 出现 22 文件）；TopBar 两端同签名不同视觉。
- 【中】worker 硬编码色 18 文件 60+；AppCard vs Card 能力不对等；用户端缺 ErrorRetry。
- 【低】Cell/CellRow、Empty/EmptyState 命名分叉；StatusDot/TabHeader/PricePill 近闲置。
- 主因排序：组件存在但不用（纪律/门禁缺失）＞ 一端缺失（按钮）＞ 缺令牌（放大器）＞ 设计稿分叉（仅 TopBar 一处有据）。
- 建议：用户端补 PrimaryButton 收编 28 调用点；TopBar 视觉参数化合并两端实现；`Color(0xFF` 仅限 theme/Color.kt 的 CI 门禁。

### 周险 · 综合评估
- 定性："两套各自成立的标准 + 一套正在繁殖的违章建筑"；三层风险：改法零成本、约定不成文、RN 族先例效应。
- 冲突取舍：支持沈标不统一主色（加"同端同槽不允许多值"硬约束）；RN 族"单源化"与"并入"分层执行（先做单源化，并入待设计裁决）；TopBar 合并与规则成文捆绑立项；按钮按"SubmitButton 唯一标准实现"收编。

## 三、Battle 记录：林师 vs 赵构（骨架之争）

- 冲突点：林师 F1 判"骨架/背景三方案并存=高、OrdersScreen 一级页自身分裂"；赵构判"骨架双层收敛、不构成结构性多套标准"；沈标附议"OrdersScreen 是否 bug 证据不足"。
- 第 1 轮：主持人向林师转述三点质询（孤例定性 / 双层标准合法性 / OrdersScreen 判定依据）。
- 林师独立抽查后**被说服**：① SignScreen.kt:71 白底系签名画布功能必需，撤回"三方案并存"；② 二级页 TopBar 流（34 文件 39 处调用）本身是双层标准下半层，撤回"丢了骨架"；③ 实测用户端 5 个一级 tab 同为"2 Pinned + 3 非 Pinned"，两端对称，OrdersScreen 非破口而是未明文化的既有约定。
- 结果：F1 由「高」降为「中」；F2 硬编码颜色维持「高」。被说服原因：对方论据经独立抽查成立，且指出其"引用代采数据未核实语义"的方法论失误。
- 方法论教训（记入规范）：引用代采统计前须打开文件核实语义。

## 四、共识

1. 两端二级页骨架/顶栏高度收敛，不存在"每页各画各的"。
2. "一级页浏览型 tab 用 Pinned 渐变、列表/功能型 tab 用普通表面；二级页统一 TopBar 流"是两端对称的既有约定，须成文。
3. 最高优先级问题：师傅端 60+ 硬编码颜色（高）、用户端共享按钮缺失+按钮四规格（高）、RN 族第二色板需设计裁决（高）。
4. 治理主路径：CI 门禁堵繁殖 → 规则成文 → 存量收编 → 美学长尾。
