### 老周（后端架构师）
- 纲：**测权限别信码表、只信探针**——三层各打"正例+越权反例"。
- 探针：菜单用 `/menu-perms` 矩阵做基线、`/auth/me` 比对；功能层必须每角色实打 2~3 个越权接口期望 403；数据层 partner 走 le 硬隔离，**期望空集/404 而非 403**（行过滤型隔离常静默截断）。
- 造号：API 建号优先（哈希/关联/审计链一致）；仅内置角色 0 账号时可 SQL 直插但须同哈希算法；密码 e2e 前缀+随机后缀；红线"验收造数不过夜"。

### 小林（前端工程师）
- 纲：**三层断言缺一不可，语义不同**——API 层断"数据对"，UI 层断"渲染符合设计"，直访 403 只能由后端断"安全"。
- 仅测 `/auth/me` permissionCodes 会假阳性：`canAccess`（role-menu.ts L51）对内置角色走 ROLE_GROUPS 组级短路，permissionCodes 不参与；菜单不渲染 ≠ 路由不可达，直访必须逐页验。
- 两套真相源（ROLE_GROUPS 硬编码 vs 后端 role_permissions 种子）必须机械对账进 CI，不许靠人眼。
- technician 定性：运行时 role 为 string，类型不含 → 静默兜底仅 overview，属预期外行为而非安全漏洞；验证三步（实登/直访/带 token 调接口）。
- 产出基线附件：`meeting-minutes/2026-08-28-menu-perm-diff-baseline.md`（9 角色 FE/BE diff 全表，16 组 85 页口径）。

### 安琪（安全审计）
- 纲：最大风险不是"权限配错"，而是三处**"默认放行"**：无 permCode 中间件的接口任何登录角色都能打、region_scope 空值语义未定、15 个有效测试 sysadmin 号是现成跳板。
- 垂直越权：technician/ops/partner_admin token 打建号、改角色、系统配置写接口，命中即权限缺失；**admin 全接口扫描 + technician 复扫**，200 差集即全体登录角色暴露面清单。
- 水平越权：pt_18639118753(le=9) 读 le=7/15/21 订单（列表参数 + 直改单号两条路）；kefu_xu(le=1) vs kefu_zhao(le=2) 订单交集应为空；partner_staff 与同 le partner_admin 对照。
- 生命周期：停用号 verify_e2e 登录应拒、存量 token 应失效；降权后旧 token 打高权接口应立即 403。
- 纪律：sec-audit-日期命名、强口令、当天停用清理；存量账号角色与 scope 一律不动；跨企业只验"可见可读"，写操作打到 403 判定即止。

### 何平（产品验收）
- 纲：预期基线必须**"双源对齐后冻结"**——后端种子与前端 ROLE_GROUPS 是两份独立事实，开测前先出 diff 对齐表（已由小林交付）。
- 基线表：ops→10 组/region 内数据；asset_admin→overview+ams/资产域；resource_admin→overview+oss+provision+aaa/资源告警域；analyst→overview+intel/只读聚合；sysadmin→全组(除 partner)/全量；partner_admin→仅 partner/本企业；partner_staff→overview+partner/本企业且功能更窄。
- 判定：菜单藏了但接口直调 200/回数据=最高危 bug；种子与 ROLE_GROUPS 漂移致可见性错=bug；"看不到某菜单"=配置非 bug（training.md 口径）；未知角色兜底属防御设计。
- 通过标准：9 类账号 100% 建号登录；正向 0 误伤 403/500；反向越权矩阵 100% 拦截、0 数据回显；每角色跨区/跨企各 ≥10 条探测 0 泄漏；权限变更即时生效可复现。
- customer 不进后台 UAT（C 端独立验收）；technician 的 dispatch_li 定性脏数据开清理工单。

## 四、Battle 记录：何平 vs 老周（跨企业拦截判定口径）

- **起因**：何平基线表写死「partner 跨企业一律 403，非 403 即不通过」；老周反驳「legal_entity_id 行过滤型隔离期望空集/404 而非 403，按 403 判会把正常实现误判为 bug」。不相容，安排正面对辩。
- **第 1 轮（何平）——被说服，修正立场**：承认「一律 403」是把功能层 permCode 拦截语义误套到数据层行过滤的实现假设，需求原文只说"越权访问被拒绝并提示"未规定状态码，收回。给出分层 oracle：功能层 403+统一提示；数据层列表空集/单资源 404 属隔离，**真正的泄露信号是"可区分性"**（越权存在 ID vs 全局不存在 ID 双请求对照，404 响应 body/错误码可区分即存在性泄露；列表空集但 total>0 同罪）；写路径信落库不信回包。
- **第 1 轮（老周）**：读码取证后抛出更重实锤——**订单详情接口没接数据范围过滤**：`GetByNo` 只按 order_no 查（pg_query.go L55），`DataAuthz` 中间件定义于 auth.go L75 但全仓零接线，跨企直读订单详情实际是 **200+数据回显**，这是真 bug，不辩解。同时论证"404 泄存在性"在本项目行过滤路径上不成立（他企与不存在走同一 WHERE、同一 ErrOrderNotFound、同响应体）。
- **主持人复核**：老周两条代码证据均属实（见本纪要第二节第 3 条）。
- **第 2 轮（老周）——确认收敛**：认可何平 oracle 三点，与实现对齐；补充执行注释：①admin 详情直读今天会以 200+回显失败，是预期红字（正是要修的洞），不是 oracle 错；②可区分性以 body/错误码为主判据，耗时可比性弱容差放宽；③详情族补过滤时 cancel 等按 orderNo 寻址的写路径同用 GetByNo，同一个洞要一起盖。
- **收敛结论（双方一致，无需裁决）**：
  1. 功能层越权：统一 403 + 统一错误格式（`{"code":403,"msg":"no permission:<码>"}`）。
  2. 数据层越权：同接口家族内"不存在/他企/越区"三情形状态码+报文**不可区分**即隔离成功；404 本身不是失败，**可区分的 404 才是**；列表空集但 total>0 判 FAIL。
  3. **硬红线：200+数据回显，见一个算一个 bug，一票否决。**
  4. 写路径判定信 DB 复核不信回包。

## 五、已证实/澄清的疑点

| 疑点 | 结论 | 依据 |
|---|---|---|
| ① technician 的 dispatch_li 挂后台 | **实锤**：后端授权 6 页（dispatch/order/provision/provlog/quadlink/scanlog），前端类型不含 technician → 兜底仅渲染工作台，6 项授权在 web 端完全不可达 | 小林 diff 表 + role-menu.ts L28 兜底 |
| ② sysadmin 前端全量菜单 vs 后端显式行 | 当前**零漂移**（82/82 对齐，唯一差异 `menu:ai` 前端缺页），但属结构性风险，需 CI 门禁防回归 | 小林 diff 表（menu-perms 实测） |
| ③ region_scope 空值语义 | **空 = 全集团**（service.go L25 注释），与老周"疑似全量"推断一致；仍需 D 组实测双重确认 | 主持人读码 |
| ④ e2e-/loadtest 临时 sysadmin 号堆积 | 认可为高风险（17 个 sysadmin 含大量有效临时号），建议清理 + 纳入每日巡检门禁 | 全员共识 |
| ⑤ partner-audit 授权给企业管理员语义可疑 | **不是错授**：000121 定义为"企业工作台·渠道审计报表"，消费端 `GET /partner/audit-report`，查询强制 `WHERE legal_entity_id=$1`；属前端缺页/文案问题，权限不动 | 老周查码（partner.go L30、pg_audit.go L21） |
| ⑥ `menu:dashboard` 仅授 analyst+sysadmin | `/dashboard` 接口确实消费 `menu:dashboard`（dashboard.go L19），其余角色直连必 403。**已裁定（何平）：分层执行——A 为 P0 基线修复**（落地页由 /menu-perms 驱动到首个有权菜单，适用全部九类角色）；**B 仅作增强立项**（只可能给 ops，且前置=老周书面确认 /dashboard 数据按 region_scope/legal_entity 过滤并落档 data-layers.md；partner 双角色明确不授，防跨企聚合泄露） | 老周查码 + 何平裁定 |
