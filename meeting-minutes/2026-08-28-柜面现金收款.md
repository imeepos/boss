# 会议纪要：后台柜面现金收款功能

- 日期：2026-08-28
- 议题：后台添加收款功能——客户不走线上付款，在营业厅当面现金支付，admin 后台如何登记收款
- 与会人：陈磊（后端架构）、苏婉（产品经理）、周敏（财务对账）、林可（前端工程师）、郑凯（风控审计）

## 一、议题背景与现状核实（成员共同查证）

- admin 已有收款端点 `POST /payments`（`internal/httpapi/admin/tax.go:22`，权限码 `menu:payment`）：流水落账 + 账单置 PAID 同事务，pay_no UNIQUE 幂等，收款成功自动出 OR- 收据、欠费客户自动复机（stop_resume_tasks RESUME 留痕）。
- 缴费方式枚举 method=wechat/alipay/card/cash/offline 已在契约（terms.md §4）；2026-09-05 裁定：师傅现场代收（现金/扫码/POS）统一记 offline。
- payments 表 000068 起双挂 bill_id（可空）+ customer_id：账单缴费走 bill，充值/预存类仅挂 customer。
- 缺口：`POST /payments` 不校验 method（任意字符串可落库）、审计 `RecordAudit("payment.record", detail=nil)` 不含金额、无营业厅/操作员凭证要素、无现金日结与限额控制；admin 前端 payment 页只有流水列表，无收款入口。

## 二、各成员发言要点

**陈磊（后端架构）**：复用现有 `POST /payments`，不新做端点；模型零变更。柜面现金记 cash（offline 专属师傅现场代收）。必补：method oneof 白名单校验（当前 BindBody 不校验，脏 method 毁财务对账）、pay_no 由后端生成（PAY- 前缀序列）防空值撞号。无账单预存 bill_id 空正合充值场景。风险提示：营业厅若收扫码/POS 记 card 还是 offline 契约两可，需产品落地前裁定；Amount 为 float64，精度是存量隐患，建议后续统一改分存储，不阻塞本期。

**苏婉（产品）**：最小可用范围 = payment 页补「柜面收款」入口，覆盖四场景：① PREPAID 办单环节 4 合同收费当场现金收（未收费不派单硬约束 REQ-CL-001）；② POSTPAID 月账单现金缴清；③ ARREARS 欠费到厅补缴（顺带核销 ar_payment_promises 催收承诺）；④ 无账单预存/充值。流程：选客户→带出未结账单或选充值→录金额收多少录多少→方式 cash→提交后流水 SUCCESS+账单 PAID+自动收据+自动复机。边界：现金班次日结、实物交款属财务线下管理（后在对辩中修正，见第四节）。提出部分收款（收 50/100）账单状态口径存疑，请架构确认，否则验收无法写。

**周敏（财务对账）**：现金收款不缺落账通道，缺"钱的闭环"。paycheck 现状是渠道对账（reconciliation_batches 按 channel 建批、pay_no=channel_ref 逐行比对），"线下营业厅"在 recon_pull.go 是 manual 渠道只建批不拉单——现金无第三方单号，渠道对账对 cash 形同虚设。账实核对三角（ledger_recon）按账单聚合，只管"账-账"管不了"账-钱"；且充值类流水 bill_id 可空根本不进三角。必须补：凭证要素（营业厅/操作员/班次/实点金额，收据照走 ARN 占号）+ T+0 现金日结。退现金走既有 REFUNDED+refund_reason 留痕，发票红冲走 void/reissue 税局轨迹。合规风险：单人收钱无复核、坐支现金、收现金不开票、日结后补。

**林可（前端）**：入口放既有「缴费管理」页 `web/admin/src/pages/billing/payment/index.tsx` 工具栏，加「登记柜面收款」按钮弹内联表单——不新建页面、不新增菜单（该页现状仅 billId 过滤+列表+刷新；客户档案与欠费页均无 /payments 引用）。menu.def.ts 第 35 行 payment key 已注册，复用零路由改动。表单：账单号/客户号至少其一、金额必填>0 两位小数、方式用 Dropdown.tsx（红线禁原生 select）、券码可选；useConfirm 二次确认；成功回显 payNo 并刷新列表，提示「账单已置 PAID、已触发自动复机」。

**郑凯（风控审计）**：柜面现金收款是高风险资金入口，不能直接开放。查证：menu:payment 授予 sysadmin+ops（000003），ops 兼管调度、投诉、拆机——业务员兼出纳，违反不相容岗位分离；同一权限码看守 GET 看流水 / POST 收款 / POST refund 退款三个不相容动作。审计 detail=nil 只留 actor+pay_no，金额、method、customer_id 全缺——追责四问（谁、何时、收了多少、什么渠道）只能答一个半；审计写失败走 `[audit] WRITE FAILED` 有兜底，但 Audit 未装配时静默跳过，收款接口应强校验审计可用、不可用拒收。舞弊对应：收钱不登记→复机与流水对不平可暴露；少登记/熟人免单→应收实收差异比对告警；虚开收据→OR- 票即凭证，作废已强制 reason。录错只许作废留痕，禁止删除。

## 三、共识

1. **不新做支付端点**：复用 `POST /payments` 全链路（流水+账单 PAID 同事务、OR- 收据、自动复机、券核销、积分），权限收紧与端点复用是两件可分离的事。
2. **口径**：营业厅柜面现金记 `cash`；offline 专属师傅现场代收，柜面录入不开放 offline。
3. **首期范围**：
   - admin payment 页「登记柜面收款」入口+内联表单（字段与交互见林可方案），四场景全开；
   - 后端补 method oneof 白名单校验；pay_no 后端 PAY- 序列生成；
   - 新增独立权限码 `menu:payment:cash`，从 ops 角色回收收款入口（看流水保留 `menu:payment`），只授柜面收款岗；前端按钮级权限随之挂新码；
   - 审计 `RecordAudit` detail 补 Amount/Method/CustomerID；
   - 单笔限额硬拦：阈值走配置中心热调，首期仅对 cash 生效、仅单笔维度，超限直接拒绝并写审计留痕；
   - payments 补「网点」「柜台/班次」两列凭证要素，收款同事务落库（T+0 进库，处置可后置）；
   - 简化日结（T+0 只读报表）：按网点+操作员聚合，收入合计/退款合计/净额三列分列（退款按流水发生日归属，防跨日退款污染当日钱箱勾对），逐笔下钻含 REFUNDED 凭证及 refund_reason/refunded_at（000112 已有字段）；报表页增「实点金额」列由操作员当日回填，不平自动落 `[paycheck] DIFF` 可 grep 差异日志（附网点/操作员上下文）；操作员仅见本网点数据（datascope）。
4. **二期**（登记有截止日，不阻塞首期）：双人复核（按金额分级、小额免复核）、钱箱台账、班次交接签字、DIFF_PENDING 差异处置工作流、坐支限额管控（须在收款入口前置校验，不做事后报表）、客户详情/欠费页收款入口、Amount 改分存储。

## 四、冲突与对辩记录

**Battle A：权限与复核（陈磊 vs 郑凯）**
- 第一轮：陈磊原主张"权限复用 menu:payment 即可，单开权限码边际收益低"。郑凯反驳：一个码看守看流水/收款/退款三个不相容动作，只读财务查询岗自动获得收款与出钱权，一行代码换职责分离谈何低收益；且审计 detail=nil 追责四问只能答一个半。陈磊查证后修正：承认 ops 兼岗与审计硬伤均属实（但指出郑凯"resource_admin 也持有"表述过宽，000003 实际授予 sysadmin+ops），收回"复用 menu:payment"，接受独立权限码+审计补全，坚持复用端点、建议限额复核分期。
- 第二轮（仅剩"限额是否首期"）：郑凯最小方案——限额阈值走配置中心热调、首期仅 cash、仅单笔维度、超限拒绝+审计留痕；陈磊明确接受（成本=读一条配置+一次金额比较+拒绝分支，无新表无状态机；权限+审计拦不住已授权账号单笔巨款，敞口不对称）。
- 结果：**收敛**。首期=权限码+审计补全+限额硬拦；双人复核分期。

**Battle B：现金日结是否进本期（周敏 vs 苏婉）**
- 第一轮：苏婉原裁定"日结属财务线下管理不进本期，ledger_recon 差异表兜底"。周敏反驳两点：① ledger_recon 三边全是账面数，操作员漏登错登时三角照样自洽，兜不住"账-钱"短款也定位不到经手人；② 首期要做的"无账单预存"走充值类流水 bill_id 可空，根本不进按账单定位的 ledger_recon——兜底表兜不住首期自己的场景；收款落账同事务即 PAID+开票，日结不可后补。苏婉被两点事实说服，修正立场：本期做"简化日结"（凭证要素 T+0 同事务落库+只读日结报表），不做完整钱箱模块。
- 第二轮：周敏确认方案整体，唯一修改：收入与退款分列三列（跨日 REFUNDED 会污染当日实点勾对——短款误报、长款掩盖）；"实点金额列当日回填+不平落 [paycheck] DIFF 日志"即其回填登记义务的底线形态，接受；提醒二期坐支限额要前置校验。
- 结果：**收敛**。简化日结进首期，完整钱箱模块分期。

## 五、待定项收口决议（2026-08-28 第二环节，全员表态收敛）

1. **部分收款口径（陈磊裁定，采纳）**：条件置 PAID——账单状态枚举仅 UNPAID/PAID/OVERDUE（fields.md L550），ledger_recon 的 PARTIAL 由金额三角独立判定、与账单状态解耦；现实现 `pg_payment.go:83` 只要 SUCCESS 就无条件置 PAID 属口径错误。改为同事务"累计实收（按分）≥应收"才置 PAID，未收齐维持原状态，接口不加参数，配套改两个既有测试。
2. **柜面 method 归类（周敏裁定，采纳）**：按"资金入账通道/对账单来源"归类，不按物理动作——柜面现金记 cash、柜面扫码(QR)记 wechat/alipay、柜面 POS 记 card；offline 维持"师傅个人代收"专属语义，柜面不得占用（method 管资金通道、凭证网点/操作员列管人员归因，两者正交）。配套：terms.md 注释 card 扩为"银行卡（线上网关/柜面 POS 收单）"；渠道对账侧须登记"柜面 POS 收单"manual 渠道源，否则柜面 POS 流水挂 MISSING_STATEMENT 误报（渠道源配置列入二期 paycheck 侧配套）。
3. **审计不可用降级（陈磊裁定，采纳）**：放行但输出 `[audit] WRITER NIL ... need-manual-recovery` 可 grep 告警日志。依据：生产装配恒非空（wiring.go），nil 仅测试场景；且 RecordAudit 在落账之后调用，前置拒收等于柜面收了现金落不了账，业务事实缺口比审计缺口更大。`httpx.go:42` 现静默 return 违反项目红线，一并修复。
4. **Amount float64 改分存储**：存量精度隐患，列技术债不阻塞本期。

## 六、验收标准（苏婉起草，含对辩修正）

1. 选客户正确带出未结账单；充值类 bill_id 空、不动账单状态。
2. 录 cash 后：流水 SUCCESS、账单 PAID、OR- 收据生成、SUSPENDED 客户自动复机且 stop_resume_tasks 有 RESUME 留痕。
3. 同 pay_no 重复提交仅落一条（幂等）。
4. method 传入白名单外取值被 400 拒绝；cash 超单笔限额被拒绝且写审计留痕。
5. 无 `menu:payment:cash` 权限拒绝收款（原 menu:payment 仅可看流水）；审计含操作员+金额+方式+客户。
6. 日结报表：收入/退款/净额三列与钱箱实点勾对，不平自动落 `[paycheck] DIFF` 日志；操作员仅见本网点。
7. 渠道统计中营业厅现金不进 offline。
