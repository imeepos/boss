# BOSS 一级目录规范

> 目标：只定义仓库根目录下一级目录的职责范围和边界，不展开二级及以下实现。
> 适用：`boss/` 仓库根目录。

## 目录清单

### `cmd/`
职责：放所有可执行入口，每个子目录对应一个部署物或一个独立运行单元。

边界：
- 只放启动、装配、信号处理、进程级生命周期管理。
- 不放核心业务规则、不放表结构、不放公共工具实现。
- 同一个入口内可以装配多个域，但不能把业务逻辑写进入口层。

### `internal/`
职责：放仓库内部实现，按域和基础设施组织，是业务代码的主承载区。

边界：
- 只在仓库内可见，不作为外部稳定 API。
- 业务域代码放这里，跨域共享基础设施也放这里。
- 不向外暴露需要长期兼容的公共契约；跨进程契约应放到 `api/` 或 `pkg/`。

### `pkg/`
职责：放可被外部服务复用的公共库和跨进程稳定契约。

边界：
- 只放真正需要复用、且需要长期稳定的内容。
- 不放单个业务域的内部实现。
- 不放会频繁改动的应用层业务逻辑。

### `api/`
职责：放接口契约，是进程间通信和对外接口的单一事实源。

边界：
- `proto/` 用于 gRPC 契约。
- `openapi/` 用于 REST 契约。
- 这里不放实现代码，只放契约和契约辅助文件。
- 契约变化必须能追溯到对应实现和测试。

### `migrations/`
职责：放数据库迁移脚本，描述 schema 演进和数据修复。

边界：
- 只放可执行的迁移 SQL，按编号顺序维护。
- 结构变更、数据回填、回滚脚本要清楚区分。
- 不把临时排查脚本、手工修复脚本混入正式迁移目录。

### `deployments/`
职责：放部署相关产物和环境编排文件。

边界：
- 只放 Docker Compose、Helm、Dockerfile、观测配置等部署物。
- 不放业务逻辑和应用代码。
- 不把一次性调试脚本当成正式部署资产。

### `scripts/`
职责：放可重复执行的工程脚本，用于开发、生成、校验、压测和运维辅助。

边界：
- 只放脚本化流程，不放核心业务代码。
- 脚本应尽量无状态、可重复运行、可审计。
- 不把脚本当成正式业务实现的替代品。

### `docs/`
职责：放项目文档、契约说明、设计记录、计划、复盘和决策记录。

边界：
- 只放文档和图示，不放运行代码。
- 权威契约文档、目录规范、计划、ADR、notes 都应可在这里找到。
- 文档必须跟代码和迁移的真实状态保持一致。

### `web/`
职责：放所有前端应用，当前按三端组织：管理端、师傅端、用户端。

边界：
- 三端可以共享基础能力，但入口和页面职责要分开。
- 不把后端实现直接搬进前端目录。
- 不让三个前端互相借用私有实现，公共能力放各自的共享层或独立公共层。

## 根文件

### `README.md`
职责：仓库总览和快速开始入口。

边界：
- 只写仓库级事实和使用方式。
- 不承载具体实现细节。

### `Makefile`
职责：统一常用工程命令入口。

边界：
- 只放可复用命令编排。
- 不把复杂业务逻辑写进 Makefile。

### `go.mod`
职责：Go 模块边界和依赖管理。

边界：
- 只管理模块和依赖版本。
- 不承载项目业务说明。

## 目录边界总则

1. 一个目录只对一种职责负责。
2. 契约、实现、迁移、部署、文档、前端不能混放。
3. 新增目录前先确认它属于哪一类职责。
4. 任何目录里的文件如果开始跨职责，就该拆分。
5. 一级目录先定死，二级目录再按域或技术展开。
