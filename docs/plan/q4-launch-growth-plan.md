# 未来 3 个月开发方向与执行计划：上线放量（2026-09 → 2026-11）

> 版本 V1.0｜规划窗口：2026-09-07 起 12 周
> 战略轴：跑通真实业务并增长（上线放量）
> 上位文档：`docs/plan/three-year-roadmap.md`（三年）、`docs/plan/q4-stable-release-plan.md`、`docs/plan/q4-open-platform-plan.md`
> 配套发散全景：`docs/plan/q4-launch-growth-ideation.md`
> 使用方式：每周一读本文件；每两周一个里程碑验收；一切验收以真实 102 环境 `http://192.168.0.102:28080` 为准，禁 mock。

## 1. 为什么是"上线放量"

今天的能力底子（已具备，不再重复建设）：

- 后端 9 阶段三期闭环：订单 12 环节状态机、四码、AAA 话单、下发/采集、GIS、分析，全部有真实实现。
- 21 能力域契约，17 域落地；开放平台 M1–M6 全量合入；指标目录 + 质量规则 + 补偿任务中心已成底座。
- 三端齐备：admin（web + Tauri 桌面）、user 门户（HTML 35 页 + Android App 已上线证据入库）、worker（web + Android 工程存在）、开放 API。
- 真实支付已通：Stripe + Cloudflare 隧道自愈守卫、付费/预付费双模式、钱包语义 9-03 已裁定。
- 营销底座已建：PROMO 券模板/兑换码/转赠、LOY 积分账本/换券；CMS 官网文章；渠道 CH 入驻审核先行。

放量的真实卡点（现状即缺口）：

1. 供给侧没有移动工具：装维现场还依赖手工/桌面，worker Android 工程存在但未发布，现场是放量的人力瓶颈。
2. 增长引擎只有底座没有活动：券、积分、渠道都建好了，但没有"活动剧本"，没有获客-转化-留存一条链。
3. 真实业务链路未经真实流量：实名、装维、税务是纸面闭环，支付回调依赖隧道漂移守卫，稳定性靠人盯。
4. 运营靠人工：对账、异常、派单、客服响应没有系统化，放量后必然失控。

结论：3 个月只做三件事——真实链路稳态、现场工具放量、增长引擎点火，外加一条贯穿的"运营守夜"辅线。

## 2. 开发方向（收敛后的三个主方向 + 一条辅线）

### 方向一：真实链路跑通与稳态（把"能演示"变成"能收钱"）

| 项 | 内容 | 验收 |
|---|---|---|
| 1.1 | Stripe 隧道守卫消抖收口：guard 收敛周期实测、URL 漂移告警接入值班渠道 | 连续 7 天守卫自愈无人工介入；漂移告警 < 5 分钟 |
| 1.2 | 支付/退款/对账全链路真实演练：幂等、双写核对、退款撤销、钱包入账 | 真实付款→退款→对账差异 = 0，全程可回放 |
| 1.3 | 话单 vs 计费每日自动轧账：RADIUS 话单 → 账单 → 缴费，差异自动派单进补偿中心 | 日报自动生成，P1 差异 4 小时清零率 ≥ 95% |
| 1.4 | 真实实名链路试跑（阿里云 CloudAuth）评估 + 税务属地（乐企/eIS）资质并行评估 | 试跑结论 + 资质评估报告（不阻塞其它里程碑） |

### 方向二：供给侧放量（现场工具 + 装维自动化）

| 项 | 内容 | 验收 |
|---|---|---|
| 2.1 | worker Android 首发：抢单池、扫码推进环节、完工证据（拍照/签名）、离线缓存、弱网重试、自更新 | 真机 + 102 真实链路装维全流程走通；发布列车出包 |
| 2.2 | 智能派单 v1：GIS 距离 + 师傅负载 + 技能匹配，人工可接管 | 派单建议可解释；接单-到场-完工时长可度量 |
| 2.3 | 环节自动化再压缩：识别剩余人工环节并自动化，人工只保留扫码与不可替代动作 | 生效环节清单 + 自动化率环比提升 |

### 方向三：增长引擎点火（获客 → 转化 → 留存）

| 项 | 内容 | 验收 |
|---|---|---|
| 3.1 | 渠道经销商 CH 放量：入驻审核、企业员工、区域权限、渠道订单（与直营共用 12 环节）、佣金台账 | 渠道可独立下单跟踪；佣金结算可对账 |
| 3.2 | 营销活动剧本：首充送券、老带新推荐码、积分兑换活动（LOY/PROMO 已有底座，只写活动规则与页面） | 至少 2 个活动上线；券/积分发放-核销-补偿全追踪 |
| 3.3 | 首单风控规则 v1（FMS 前哨）：同号多单、设备串号异地、异常地址拦截 | 规则引擎可配置；拦截/放行有审计留痕 |
| 3.4 | 官网获客闭环：CMS 文章 + App 下载 + 活动落地页 + 客服入口 | 官网到注册转化路径可追踪 |

### 辅线：运营守夜（贯穿 12 周）

| 项 | 内容 | 验收 |
|---|---|---|
| 4.1 | 每日 03:00 自动轧账 + 数据质量规则 → 异常进补偿任务中心 | 连续 7 天无人工盯守 |
| 4.2 | SLO 巡航：关键接口延迟/成功率每日采集，超阈值告警 | SLO 看板周报自动生成 |
| 4.3 | 经营驾驶舱 v1：收入/装机/资源利用率/流失/转化漏斗（指标目录底座已备） | 核心指标口径与报表一致 |

## 4. 验收指标（放量口径）

| 指标 | 目标 |
|---|---|
| 真实新装机量 / 活跃客户数 | 环比正增长（以 102 真实数据为准） |
| 订单完成率（下单→激活） | ≥ 99% |
| 浏览→下单→支付转化漏斗 | 逐环节可测、可归因 |
| 缴费率 / 续费率 | 环比提升有口径 |
| 对账差异 | = 0，且 P1 异常 4 小时清零率 ≥ 95% |
| 师傅端在线率 / 完工时长中位数 | 放量后可度量、可优化 |
| 渠道订单占比 / 活动核销率 | 有台账、可对账 |
| 核心 SLO | 与 `docs/ops/slo.md` 口径一致并持续达标 |

## 5. 明确不做（3 个月红线，防范围膨胀）

1. 不拆微服务；不引入多区域/多法人复制（等第二区域环境）。
2. 不做 AI 自动决策与预测性维护（等 LLM key 与真实设备数据；规则 + 人工复核先行）。
3. 不铺 WHO/RA/FMS/SET 大域（本计划只做 FMS 前哨规则，其余业务场景未明确）。
4. 不做税务对接开发（仅资质与方案评估，随支付/装维主线并行）。
5. 不新增页面壳子：上线改造前先做死功能审计，砍掉无动作反馈的入口。
6. 不用 mock 验收：集成、回归、发布一律打真实 102 环境。

## 6. 运作机制

- 每周一读本文件；每两周里程碑评审（继续/调整/暂停/退出四态，见三年路线图 §8）。
- 发布列车：每两周一个发布窗口（灰度→回滚→发布后验证），沿用 `docs/ops/release-train.md`。
- 守夜自动化：每日 03:00 对账 + 质量规则 + SLO 采集，异常自动进补偿任务中心，人工只处理派单。
- 契约纪律：新增端点同步 `api/openapi/*` 与 `docs/contract/fields.md`；迁移号先查再占（见 AGENTS.md）。
- 提交纪律：`type(scope): subject`；一次提交一个可独立回退的变更；文档变更同样走 worktree 协议。
- 证据入库：每个里程碑验收附真实环境证据（CDP 截图、接口响应、SQL 直查），参照 `docs/ops/user-android-launch-status.md` 模式。

## 7. 风险与依赖

| 风险 | 应对 |
|---|---|
| Stripe 隧道 URL 持续漂移 | 守卫自愈已建，本计划补告警接入 + 连续观察收口 |
| worker Android 人力与 user Android 并行 | 复用 user 工程组件/模式，砍非关键动效，保主链路 |
| 渠道资质（佣金/批发结算） | CH 只做入驻+订单+台账，不碰批发结算 SET |
| 真实实名/税务资质未到 | 并行评估不开发，支付与装维主线不受阻 |
| 放量后数据质量失控 | 守夜自动化先行（M0 上线），质量异常先于业务放量可闭环 |
| 并行会话撞迁移号/契约文件 | 开工前两处查号（本树 + 未合并分支），注册类改动压独立小提交 |
