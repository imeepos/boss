# BOSS 全项目重规划执行方案

> 版本 V1.0 | 基于架构师 / DBA / 后端 / 前端 / 测试五个视角的三轮审视结果
> 定位：如果整个项目从零重做，如何重新规划设计，并把方案压成可落地、可控质量、可回滚的执行路径。

## 1. 结论先行

这套系统不适合走“先堆功能、后补约束”的路。正确顺序是：

1. 先定单一事实源和边界。
2. 再定领域原语、数据约束和契约。
3. 再长页面、工作流和异步事件。
4. 最后再考虑拆分、扩展和性能优化。

如果重做，我会把 BOSS 设计成一个**契约驱动的模块化单体**：
- Go 作为唯一后端实现语言。
- PostgreSQL 作为唯一 OLTP 真相源。
- Temporal 只做长流程编排，不做状态真相源。
- Kafka 只做事实事件广播，不承载业务决策。
- OpenAPI / Protobuf / 数据契约三者必须同源。
- 前端按角色和任务组织，不按后端包名组织。
- 测试以契约、状态机、回放和主链路门禁为核心。

## 2. 第一步：目录规划

先不碰复杂架构，第一步只做目录边界和职责划分。目标是让后续任何一个域、前端页面、测试用例、迁移脚本，都能在目录上找到唯一落点。

### 2.1 后端目录

```text
internal/
  app/                 # 装配、启动、路由、依赖注入
  domain/
    <domain>/
      command/         # 写请求入口
      domain/          # 聚合、值对象、状态机、领域规则
      repository/      # 持久化实现
      projection/      # 读模型、查询视图
      transport/       # HTTP / gRPC 适配
  pkg/                 # 跨域基础设施（auth、audit、middleware、server 等）
```

目录原则：
- 一个域只在自己的目录里写核心规则。
- `internal/pkg` 只放跨域基础能力，不放业务规则。
- 入口层和领域层分开，适配层不许写业务决策。
- 新域先补目录，再补代码。

### 2.2 数据目录

```text
migrations/
  000001_*.sql
  000002_*.sql
  ...

migrations/
  _archive/            # 已废弃但保留记录的迁移说明
```

目录原则：
- 结构变更和数据回填尽量分开。
- 审计、事件、历史类表单独归类说明。
- 迁移文件只记录一次性变更，不把临时脚本混进来。

### 2.3 前端目录

```text
web/
  admin/               # 管理端
    src/
      app/             # 路由、权限、主题、i18n
      features/        # 按角色和任务组织页面
      entities/        # 实体、状态、枚举映射
      shared/          # api、ui、hooks、permissions、utils
      tests/
  worker/              # 师傅端
    src/
      app/
      features/
      shared/
  user/                # 用户端
    src/
      app/
      features/
      shared/
```

目录原则：
- 页面按任务，不按后端包名。
- `shared/api` 是唯一请求入口。
- `shared/permissions` 管权控，不在页面里散写角色判断。
- admin、worker、user 三端分目录，但共享同一套基础约束。

### 2.4 测试目录

```text
internal/
  app/
    e2e_*.go          # 主链路集成测试
    contract_*.go     # 契约对账测试

web/
  admin/
    e2e/
    tests/
```

目录原则：
- 契约测试和主链路测试分开。
- 每类测试只负责一个风险面。
- 测试数据、测试夹具、回放样例单独放置。

## 3. 三轮讨论记录

### 第 1 轮：五个视角分别审视

#### 架构师视角
- 重点问题不是功能少，而是流程语义重叠：状态机、Temporal、Kafka 三套机制同时推进同一业务，容易出现双重事实源。
- 最该前置的是域边界、事件边界、状态边界，尤其是订单、计费、AAA、资源这几个高耦合域。
- 不建议过早微服务化，当前阶段更适合把模块化单体打硬，把边界打清。

#### DBA 视角
- 最危险的是跨域写入缺少强约束，状态和事实混存，历史和当前态口径不统一。
- 先做约束，再做索引；先做主表/事件表/历史表分层，再做分区和归档。
- 地址层级、订单阶段、端口占用、四码合一都要在数据库层明确唯一性和一致性。

#### 后端视角
- 最容易爆炸的是“命令、状态机、工作流、事件”混写。
- 最该抽象的是聚合、命令、事件、读模型这四个原语。
- 进程内对象和跨进程契约必须彻底分开，DTO 不能到处复用。

#### 前端视角
- 前端不应按后端域直接硬切菜单，而应按角色和任务组织。
- 需要统一 role-view model、权限边界、契约驱动客户端、状态管理分层。
- 设计系统要先统一列表、表单、详情、流程页骨架，再谈视觉风格。

#### 测试视角
- 主风险不是纯算法，而是跨域联动、异步最终一致性、迁移回滚、测试数据污染。
- 测试金字塔要重排：契约测试和状态机测试优先，E2E 只保留主链路。
- 发布前必须有迁移演练、回滚演练和关键链路冒烟。

### 第 2 轮：把分歧收敛成共识

五个视角虽然切面不同，但共识很一致：

1. **先定边界，再做功能**
   - 架构、后端、DBA 都认为，边界不稳时继续堆功能只会放大耦合。

2. **先定契约，再做页面和服务实现**
   - 前端和测试都要求契约先行；后端也认为 DTO 不能自由漂移。

3. **先做约束，再做优化**
   - DBA 明确指出约束比索引更重要；后端和测试也要求先把幂等、状态转移和回放做硬。

4. **主链路优先于边角功能**
   - 订单 12 环节、开户实名、资源预占、AAA、工单、GIS、报表是主干，其余都要围绕这些链路收口。

5. **质量门禁必须前置到提交和合并阶段**
   - 不能把问题留到上线才发现，必须在契约、状态机、迁移和路由层就拦住。

### 第 3 轮：形成最终执行原则

最终执行原则压成 8 条：

1. 单一事实源优先。
2. 领域边界优先。
3. 契约先行。
4. 约束先于索引。
5. 事件和状态分离。
6. 前端按角色和任务组织。
7. 测试按风险而不是按页面平均分配。
8. 发布必须可验证、可回滚、可追踪。

## 3. 目标架构

### 3.1 后端总体形态

推荐目标形态：**模块化单体 + 清晰域边界 + 统一编排原语**。

- `internal/domain/*` 仍按业务域分包。
- 每个域内部按 `command / domain / repository / projection` 划分。
- `internal/pkg/*` 只放真正跨域的基础设施，不放业务规则。
- `Temporal` 只编排长流程，不直接改业务真相。
- `Kafka` 只传事实事件，不传控制命令。
- `HTTP/gRPC` 只是适配层，不写核心规则。

### 3.2 数据总体形态

推荐目标形态：**主表 + 事件表 + 历史表**。

- 主业务表只保存当前态。
- 事件表保存可回放事实。
- 历史表保存审计、回调、状态流转和快照。
- 所有关键写入都带幂等键、trace id、版本号和时间戳。
- 只有高增长时序表做分区，且必须有 DEFAULT 分区兜底。

### 3.3 前端总体形态

推荐目标形态：**契约驱动的运营工作台**。

- 页面按角色和任务组织。
- 权限用统一 role-view model，不在页面里散写判断。
- API 通过 OpenAPI 生成 client 和类型。
- 状态分层：URL 状态、请求状态、业务状态、全局状态分开管理。
- 设计系统先统一业务骨架，再统一视觉细节。

### 3.4 测试总体形态

推荐目标形态：**契约测试 + 状态机测试 + 主链路回放测试 + 少量 E2E**。

- 契约测试保住字段、枚举、状态、错误码。
- 状态机测试保住合法/非法迁移。
- 回放测试保住异步幂等和补偿。
- E2E 只保留少量主链路和发布门禁。

## 4. 分阶段执行路线

### 阶段 0：定规矩

目标：把不可逆决策先定住。

交付物：
- 契约目录和目录边界说明。
- 领域边界和职责矩阵。
- 状态机、事件、工作流的职责定义。
- 迁移和审计的统一规范。

验收标准：
- 每个核心域都能说清楚“谁写真相、谁只编排、谁只展示”。
- 所有跨进程契约有单一来源。

### 阶段 1：打骨架

目标：把工程骨架、基础设施和门禁先落地。

交付物：
- 后端四层目录骨架。
- 契约生成链路。
- 数据迁移和回滚规范。
- 前端应用骨架和设计系统骨架。
- 测试门禁骨架。

验收标准：
- 新增一个域时，不需要重新发明结构。
- 所有接口变更能在 CI 中被捕捉。

### 阶段 2：打主链路

目标：先把最重要的业务链路跑通。

主链路优先级：
1. 注册 / 认证 / 权限
2. 客户开户注册 / 实名
3. 资源核查 / 端口预占
4. 订单 12 环节
5. AAA / 计费 / 停复机
6. 工单 / 配置下发 / 采集告警
7. GIS / 分析 / 报表

验收标准：
- 每条主链路都能从前端点到后端真相源。
- 每条主链路都有契约测试和回放测试。

### 阶段 3：打防线

目标：把易坏点变成受控点。

交付物：
- 状态机非法迁移测试。
- 幂等、重试、补偿测试。
- 迁移演练和回滚演练。
- 关键指标和链路追踪看板。

验收标准：
- 线上事故可以回放、定位、补偿。
- 变更不靠人工盯盘。

### 阶段 4：再谈扩展

目标：在边界稳定后再决定拆分、性能和增量域。

交付物：
- 可拆分边界评估。
- 性能瓶颈清单。
- 新域接入模板。
- survey 和债务代谢机制。

验收标准：
- 新域接入是复制模板，而不是重新造轮子。
- 拆分决策有明确收益而不是情绪驱动。

## 5. 各角色落地要点

### 架构师要盯的事
- 状态机、Temporal、Kafka 的边界必须写进 ADR。
- 域边界和依赖方向必须可读、可查、可审。
- 所有不可逆决策当天写 note。

### DBA 要盯的事
- 约束优先级高于索引。
- 主表、事件表、历史表分离。
- 高增长时序表才分区，且要有兜底分区。
- 迁移必须可重放、可回退、可审计。

### 后端要盯的事
- 聚合、命令、事件、读模型要统一建模。
- 进程内对象和跨进程契约分离。
- 错误码统一。
- 任务和事件分离。

### 前端要盯的事
- 页面按角色和任务组织。
- OpenAPI 生成类型和 client。
- 权限、状态、URL、请求分层管理。
- 设计系统先统一业务骨架。

### 测试要盯的事
- 契约测试放第一层。
- 状态机测试覆盖合法/非法迁移。
- 主链路回放测试兜住幂等和补偿。
- 发布前要有迁移演练和回滚演练。

## 6. 质量门禁

### 提交前
- 格式检查。
- 静态检查。
- 契约快照校验。

### 合并前
- 单测通过。
- 契约测试通过。
- 状态机测试通过。
- 最小集成测试通过。

### 发布前
- 迁移演练通过。
- 主链路冒烟通过。
- 回滚演练通过。

### 发布后
- 健康检查通过。
- 关键指标在阈值内。
- 事件延迟和错误率稳定。

## 7. 风险清单

1. **双事实源风险**
   - 风险点：状态机、Temporal、Kafka 同时推进同一事实。
   - 处理：明确单事实源，Temporal 只编排，Kafka 只发事件。

2. **契约漂移风险**
   - 风险点：OpenAPI、Proto、前端类型、数据库字段不同步。
   - 处理：契约生成与 CI 门禁。

3. **数据污染风险**
   - 风险点：测试数据共用、回归环境污染。
   - 处理：独立环境、一次性数据、自动清理。

4. **迁移事故风险**
   - 风险点：大迁移不可回退。
   - 处理：结构变更与数据回填拆开，先演练再执行。

5. **前端权限混乱风险**
   - 风险点：角色判断散落在页面里。
   - 处理：统一 role-view model。

## 8. 最终建议

如果现在就开始重做，我会按下面顺序动手：

1. 先冻结契约和边界。
2. 再把主链路抽成状态机和事件模型。
3. 再把数据层改成主表 / 事件表 / 历史表。
4. 再重建前端信息架构和设计系统。
5. 最后把测试门禁补成默认流程。

这不是“把现有项目推倒重来”，而是“把已经验证过的业务知识重新编码成更硬的机制”。

## 9. 可执行验收口径

当这套重规划真正落地后，至少应满足：

- 任一主链路都能明确说出单事实源是谁。
- 任一字段变更都能追到契约和测试。
- 任一状态变更都能回放、追踪、补偿。
- 任一发布都能验证、回滚、审计。
- 任一新域都能用模板接入，而不是重新发明结构。
