# BOSS 平台未来三年开发计划

> 版本 V1.0｜规划周期：2026 Q4—2029 Q3（36 个月）
> 定位：在现有 9 阶段、三期业务闭环和 21 能力域契约基础上，指导产品、架构、研发、交付的滚动排期。
> 使用方式：季度复盘一次；每季度只承诺可验收的目标，不以功能数量代替业务结果。

## 1. 规划基线

### 1.1 已具备能力

- 后端采用 Go 模块化单体，PostgreSQL 是 OLTP 真相源；订单 12 环节状态机、outbox、审计、OpenAPI、gRPC 和 Kafka 事件链路已形成基线。
- 收款闭环、服务闭环、经营闭环的核心服务端能力已完成第一轮实现；GIS、经营分析、报表、可观测、压测和 Helm 上线能力已有基础。
- Admin 已有按能力域组织的页面和权限体系，三端接口前缀隔离：admin、user、worker。
- 契约事实源为 `docs/contract/{terms,domain-map,fields}.md`；其中 21 个能力域仍有 CS、AR、WHO、RA、FMS、SET、PORT 等待建或未完整覆盖的部分。

### 1.2 三年总目标

到 2029 Q3，形成一个可规模化运营的综合业务支撑平台：

1. **业务完整**：客户、产品、订单、资源、装维、AAA、计费、客服、渠道、营销、分析形成端到端闭环。
2. **平台可靠**：关键交易可幂等、可追踪、可回放、可补偿；发布可灰度、可回滚，数据可恢复。
3. **多端协同**：Admin、客户门户、师傅端和开放 API 使用同一契约与权限模型，减少重复建设。
4. **数据可经营**：指标可解释、口径统一、数据质量可监控，分析结果能回到运营动作。
5. **可复制交付**：部署、初始化、升级、培训、验收标准化，支持多法人、多区域、国际化落地。

## 2. 三年路线总览

| 年度 | 阶段定位 | 核心结果 |
|---|---|---|
| 第一年：2026 Q4—2027 Q3 | 产品化与生产稳态 | 把已有闭环从“能跑”提升为“可运营、可交付、可观测” |
| 第二年：2027 Q4—2028 Q3 | 业务扩展与生态连接 | 补齐客服、应收、渠道、营销、门户等增长能力，建立开放集成平台 |
| 第三年：2028 Q4—2029 Q3 | 智能经营与规模复制 | 以数据、自动化、AI 和多租户交付支撑多区域规模化运营 |

## 3. 第一年：产品化与生产稳态

### 年度目标

完成现有一期、二期、三期能力的生产化收口，优先解决“流程可用但运营成本高、异常处理依赖人工、数据口径不稳”的问题。

### 2026 Q4：基线冻结与生产补强

- 冻结订单 12 环节、状态枚举、字段命名、错误码和三端 OpenAPI/Protobuf 契约。
- 完成主链路验收：客户实名 → 产品订购 → 资源预占 → 合同收费 → 派单 → 扫码 → 激活 → 回调 → GIS 更新。
- 建立生产数据初始化、迁移回滚、备份恢复、告警值班和事故处理手册。
- Admin 完成高频页面与真实 102 环境联调，不再以 mock 作为验收依据。

**验收指标**：主链路成功率 ≥99%；关键写操作幂等覆盖率 100%；发布具备可验证回滚路径。

### 2027 Q1：运营效率与异常闭环

- 建立统一待办、消息、告警、审计和补偿任务中心。
- 完善订单超时释放、激活失败重试、支付回调重放、话单补偿、四码冲突处理。
- 完成师傅端离线扫码缓存、弱网重试和现场证据留存；Admin 支持按订单查看全链路时间线。
- 统一数据质量检查：订单阶段、四码关系、资源占用、账务流水和 GIS 投影每日对账。

**验收指标**：P1 异常均有责任队列和处理时限；四码冲突 4 小时内清零率 ≥95%；关键补偿任务可回放。

### 2027 Q2：财务、税务与交付标准化

- 完整化发票与税务域：税局回执、法定票号、作废、重试、属地配置和对账。
- 收口预付费/后付费、退款、欠费、停复机、收款渠道和账单日切边界。
- 建立租户/法人/区域数据隔离的交付模板，补齐初始化种子、权限模板和数据导入校验。
- Admin 形成统一列表、表单、详情、流程页设计系统，减少页面级样式分叉。

**验收指标**：账实核对差异可定位；发票状态与税局状态正交且可追踪；新环境按清单完成部署和初始化。

### 2027 Q3：第一年稳定版发布

- 完成全量 API 契约对账、数据库迁移演练、灾备恢复演练和容量压测。
- 建立 SLO/SLI：API 延迟、认证成功率、订单完成率、消息延迟、话单完整率、报表时效。
- 建立版本化发布列车：变更评审、灰度、回滚、发布后验证和复盘闭环。
- 发布“生产稳定版 1.0”，形成客户验收包、运维手册和实施培训材料。

**年度出口**：核心客户可持续使用；重大异常有发现、隔离、补偿和复盘闭环；新增功能不破坏契约与主链路。

## 4. 第二年：业务扩展与生态连接

### 年度目标

从“新装开通平台”扩展为覆盖客户全生命周期、合作伙伴和开放集成的业务平台，同时保持模块化单体边界，不因规模压力过早微服务化。

### 2027 Q4：客服与应收信用

- 建设 CS 客服工单域：报障、投诉、升级、SLA、知识库、回访和服务评价。
- 建设 AR 应收信用域：账龄、催收、信用等级、停机策略、承诺还款和核销。
- 将工单与订单、客户、资源、告警、装维任务关联，支持统一客户视图。
- 建立客户服务指标：首次响应、一次解决、逾期率、重复报障率。

### 2028 Q1：渠道与伙伴协同

- 完善 CH 渠道经销商域：入驻审核、企业员工、区域权限、渠道订单、佣金和结算对账。
- 提供伙伴工作台与受限 API key，区分企业、员工、客户三类主体权限。
- 支持渠道订单与直营订单共用订单状态机、资源预占和计费规则。
- 形成渠道反作弊和操作审计基础能力。

### 2028 Q2：营销、忠诚度与客户门户

- 完整化 PROMO：券模板、活动规则、兑换码、转赠、缴费抵扣和赠送时长。
- 完整化 LOY：积分账本、等级、任务、自动积分、积分回滚、过期和兑换补偿。
- 建设 PORT 客户门户：产品浏览、订购、缴费、发票、工单、进度、券和积分。
- 统一客户、账号、认证、API key 与数据域权限，避免三端身份体系分裂。

### 2028 Q3：开放平台与互操作

- 建设版本化开放 API、Webhook、事件订阅、签名校验、限流和开发者文档。
- 对接支付、短信、实名、税务、地图、设备、RADIUS/AAA 等外部系统，适配器隔离供应商差异。
- 建设沙箱、契约测试、回放样例和集成方自助验收工具。
- 评估高负载或组织边界明确的能力是否需要独立部署；迁移必须保持事件和 API 兼容。

**年度出口**：客户从获客、订购、交付、使用、缴费、报障到续费有完整数字化旅程；渠道和外部系统可自助接入。

## 5. 第三年：智能经营与规模复制

### 年度目标

将平台从业务系统升级为经营与自动化平台，重点是跨域决策、预测性运维、自动化执行和多区域复制，而非单纯增加页面。

### 2028 Q4：经营数据平台

- 建立统一指标目录、数据血缘、口径版本、维度模型和数据质量规则。
- 将订单、客户、资源、AAA、账务、工单、渠道、营销数据形成可追溯主题域。
- 支持区域、法人、渠道、产品、客户生命周期等多维经营分析。
- 建设经营驾驶舱：收入、欠费、装机、资源利用率、服务质量、流失和营销转化。

### 2029 Q1：AI 辅助运营

- 引入 AI 能力网关，统一模型配置、密钥引用、审计、成本和调用限额。
- 优先落地低风险场景：客服摘要、工单分类、知识检索、异常解释、报表问答和运营建议。
- AI 只提供建议或草稿；涉及收费、停机、资源释放、权限和合同的动作必须人工确认或经过规则引擎。
- 建立评测集、敏感信息脱敏、提示词版本、结果审计和人工反馈闭环。

### 2029 Q2：自动化网络与预测性维护

- 基于设备指标、告警、工单和资产历史，建设故障预测、容量预测和维护优先级。
- 将规则、事件、任务、补偿和人工审批统一为可视化自动化编排。
- 支持资源扩容、设备更换、派单和回访的半自动决策，保留人工兜底。
- 以 ODN/GIS 数据支撑区域建设规划和资源投资分析。

### 2029 Q3：多区域规模化交付 2.0

- 完成多法人、多区域、多语言、多时区、多币种和税务属地能力的产品化。
- 建立租户级配置、功能开关、数据保留、备份恢复、容量配额和升级策略。
- 发布标准化实施包：环境检查、初始化、迁移、验收、培训、监控接入和运维交接。
- 评估模块化单体拆分边界，仅对有独立伸缩、故障隔离或组织自治价值的域拆分。

**三年出口**：平台可复制到新区域和新法人，运营决策有数据依据，自动化有边界和审计，核心系统可持续演进。

## 6. 横向工程主线

以下工作贯穿 36 个月，不能作为某个季度的“有空再补”：

| 主线 | 第一年 | 第二年 | 第三年 |
|---|---|---|---|
| 契约治理 | OpenAPI/Proto/fields 对账门禁 | 外部 API 版本与兼容策略 | 多租户契约与数据域版本化 |
| 质量 | 状态机、迁移、主链路、回放测试 | 集成方契约测试与故障注入 | 预测性质量、容量模型与混沌演练 |
| 安全 | RBAC、审计、密钥引用、备份 | API key、伙伴隔离、反欺诈 | AI 安全、租户隔离、合规审计 |
| 可观测 | 日志、Trace、Metrics、告警 | 业务 SLO 与成本监控 | 跨租户容量与智能告警 |
| 数据 | OLTP 与投影对账 | 主题域与指标目录 | 数据血缘、预测模型与经营闭环 |
| 交付 | 102 环境验收与回滚 | 沙箱、开放平台、自助接入 | 多区域模板化部署与升级 |

## 7. 取舍与明确不做

1. 不以“拆微服务”作为三年目标；先保持模块化单体，只有出现明确的伸缩、隔离或自治需求才拆分。
2. 不让 Kafka、Temporal 或 AI 成为业务真相源；状态机和 PostgreSQL 仍负责业务事实，事件只做广播，编排只做调度。
3. 不把所有历史域一次性补齐；按客户价值和主链路优先，WHO、RA、FMS、SET 等域在业务场景明确、边界和验收标准具备后再建设。
4. 不用 mock 代替真实后端验收；开发可用 mock，集成、回归和发布必须对接 102 部署环境 `http://192.168.0.102:28080`。
5. 不把 AI 直接接入高风险自动决策；先做可解释、可审计、可人工确认的辅助场景。

## 8. 季度治理机制

每季度结束前完成一次“目标—指标—风险—债务”复盘：

- **继续**：业务指标达成且架构边界稳定的工作，进入下一季度滚动计划。
- **调整**：价值成立但依赖、成本或范围变化的工作，重排优先级并更新契约。
- **暂停**：没有明确业务结果、会扩大耦合或缺少验收条件的工作。
- **退出**：连续两个季度没有使用价值或可被平台能力替代的功能，记录决策后停止。

每项年度目标必须有负责人、依赖域、契约入口、验收指标、上线窗口、回滚方案和文档归档位置。任何不可逆架构或数据决策，按 `docs/notes/adopted/` 制度当天留档。
