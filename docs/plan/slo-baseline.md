# 性能与 SLO 基线

## 当前基线

已知 100 VU 压测结果：读路径 P95 **574ms**，登录 P95 **858ms**。数据来自现有 k6 脚本与压测记录；本轮未向 102 写入数据、未部署代码。

## 目标与依据

- 关键读路径 P95 < **400ms**。
- 管理端登录 P95 < **600ms**。
- 错误率 < **1%**。

目标相对已知基线分别留出约 30% 性能改善空间，并为数据库抖动、网络与 100 VU 并发保留余量；目标是用户可感知的交互级 SLO，而非单条 SQL 延迟。

## 优化项、预期收益与验证

| 优化 | 机理 | 预期收益 | 验证方法 |
|---|---|---|---|
| 订单状态/客户+ID DESC 索引 | 过滤和倒序分页减少排序与扫描 | 订单列表在高基数数据下减少扫描，目标 50–150ms | 部署后运行 `k6 run -e BASE=http://192.168.0.102:28080 -e TARGET=100 -e LOAD_USER=... -e LOAD_PASS=... scripts/load/api-load.js`，比较 `http_req_duration` |
| 分析关联索引 | 为端口、支付账单、扩容区域和维护排序提供索引 | 分析/报表聚合减少全表扫描，目标 30–120ms | 同上；单独观察 `/analytics/indicators`，必要时在 102 只读执行 `EXPLAIN (ANALYZE, BUFFERS)` |
| 列表默认 LIMIT | 避免未传 limit 时退化为约 1GiB 的无限列表 | 限制响应体和扫描上界，尾延迟收益取决于数据量 | k6 读场景 + 检查接口响应行数不超过 100 |
| 连接池默认并发 | 100 VU 需要足够但有上限的数据库连接，避免排队与过度争用 | 降低池等待尾延迟，目标 10–80ms | 部署后观察 `db_pool_acquire_seconds`/连接使用率与 k6 P95 |
