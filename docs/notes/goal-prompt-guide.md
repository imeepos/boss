# DSH Goal 提示词（objective）编写指南与模板

> 依据：DSH Goal 机制（持久化目标 + 自动续行 + Round 上限 + revision 乐观锁 + blocked 三轮规则）与社区实践整理。
> 适用：所有需要跨轮次、跨会话自动推进的长线任务。

## 1. 先判断该不该用 Goal

| 场景 | 判定 |
|---|---|
| 一次性问答 | 不用，普通对话 |
| 多步骤但一轮能干完 | 不用，普通对话 / workflow / 子代理 |
| 长线任务，跨天、跨会话，需"盯到完成为止" | 用 Goal |
| 依赖外部反馈（CI、评审、真机验证）多轮迭代 | 用 Goal |

一句话标准：**任务需要跨越多个轮次/会话、由 agent 自动持续推动**，才建 Goal。

## 2. objective 六条硬规则

1. **写成可判定的完成状态，不写动作清单。** 目标是 `complete` 的判据，不是 todo 列表。
   - 反例："优化一下性能"（无法判定何时 complete，空转烧 Round）
   - 正例："p99 < 200ms 且基准测试全绿"
2. **单一目标。** 一个 Goal 只装一个不可变目标；方向变了用 `edit`（revision 会 +1），不要口头在聊天里改。
3. **完成标准必须包含验证动作。** 写明"build + 测试全绿才算完成"，防止未验证即 complete。
4. **写明阻塞条件。** 什么情况算"撞墙"（外部依赖不可用、需要人工决策），并注明"不要绕过"。
5. **说明为什么是长线任务。** 一句话点出跨轮次的原因（等 CI、需多轮验证），模型才会合理分配每轮工作量。
6. **显式设 `max_goal_rounds`。** 默认 256 偏大；按任务量级给个更紧的上限防失控烧 token。

## 3. objective 模板

```
【目标】<一句话的最终状态，可判定>
【完成标准】
- <可度量的判据 1，如：p99 < 200ms / 121 个端点全部返回 200>
- <验证门禁：typecheck + test + build 全绿，git status 干净>
【背景/为什么长线】<一两句：为何需要跨轮次推进>
【约束】
- <不可违反的红线，如：不许改契约文档 / 不许跳过测试>
【阻塞条件】
- <遇到 X（外部依赖不可用/需人工拍板）即 block，不绕过>
【轮次上限】<N 轮（按工作量量级给紧值）>
```

使用时整体作为 create_goal 的 objective（或从用户请求中提炼后填充）。

## 4. 实例对照

### 反例（不要这样写）

> "把订单模块的性能优化一下，顺便修修 bug"

问题：无完成判据（何时 complete？）、双目标（优化 + 修 bug）、无验证动作、无阻塞条件。

### 正例

```
【目标】订单列表接口 GET /api/orders 在 1 万条数据下达到 p99 < 200ms
【完成标准】
- 压测脚本 e2e/bench-orders.ts 三轮结果均 p99 < 200ms
- pnpm typecheck && pnpm test && pnpm build 全绿
- 行为无回归：订单 12 环节状态流转测试（docs/contract/terms.md）全过
【背景/为什么长线】需先加索引再压测、按结果多轮迭代，单轮做不完
【约束】
- 不改 docs/contract/ 下任何契约字段名
- 遵循单文件 ≤300 行、单函数 ≤30 行
【阻塞条件】
- 压测环境数据库不可用即 block，不要改用 mock 数据充数
- 需要变更契约字段时 block 等人工确认
【轮次上限】12
```

## 5. 运行期操作要点

- **complete**：仅在完成标准逐条满足后标记；每条判据要有对应的验证动作证据。
- **blocked**：同一阻塞条件持续 ≥3 轮才标记，原因必须具体（"CI 挂了"不够，要写哪个 job 哪步挂）。
- **pause / resume**：主动暂停随时可恢复；会话恢复后续行不自动重启，需显式 resume。
- **edit**：方向变更走 edit，不要靠聊天纠正——旧 revision 上的修改会被拒绝。
