# 真实短信/支付渠道接入决策:网关抽象留在域内,供应商按属地商务定,凭据未到不 vendor SDK

日期:2026-08-20

## 决策

1. **系统侧自持状态的姿态不变**(延续 2026-08-18-tax-jurisdiction 与 2026-08-19-user-portal-mobile-endpoints §5):
   短信验证码以 `portal_sms_codes` 为准、支付以 `payments`+账单状态机为准,真实渠道只做"投递/收单"
   适配器,不成为记账事实源。渠道回调幂等入账,对账以本系统流水为准。
2. **短信按属地选商,不签全球单一供应商**:
   - 中国属地:阿里云短信(签名+模板报备,回执 web_hook 可查送达)。
   - 菲律宾属地(PSGC 主战场):商务比选 Semaphore / Twilio 一类,硬性门槛:支持 PH 长号码投递、
     送达回执、单价可审计;未定前维持 DB 模拟(冒烟从 DB 读码)。
3. **支付按属地双通道**:
   - 中国:微信支付 + 支付宝(标准服务商模式,回调验签后走既有 RecordPayment 同事务落账)。
   - 菲律宾:GCash + Maya(主流钱包覆盖率优先);渠道网关即支付发起方,系统只做收单回调对账。
4. **供应商 SDK 一律不 vendor、不提前入库**:接口收敛为域内 gateway 接口(短信 send/verify、
   支付 create/confirm/callback),实现以薄 HTTP adapter 落地,凭据走环境变量(引用不存值)。
5. **厂商签约/开户属商务依赖,非工程阻塞**:在凭据到位前,CI/验收以模拟通道为准;
   凭据到位当天以 Amended 方式记录最终供应商与账号形态。

## why

- 多属地税率/监管并存已是既有裁定,短信与支付同样必须按属地走,全球单一供应商在 PH 场景
  覆盖率与单价均不占优。
- 系统自持状态 + 薄适配器:渠道更换/新增是单文件变更,不动状态机;对账口径始终在本系统。
- 不 vendor SDK:避免为未签约渠道引入长尾依赖与安全审计面。

## 放弃了什么

- 放弃"签约前先接 SDK 占位":未验凭据的集成代码无法测试,只会制造假覆盖率。
- 放弃统一支付聚合商(如 Stripe 连接):PH 本土钱包费率与结算周期劣势,且记账事实源会外移。
- 放弃短信通道用于营销群发(仅验证码/工单通知,单向、低量)。
