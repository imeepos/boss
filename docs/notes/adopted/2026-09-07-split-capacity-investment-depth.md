# 2026-09-07 分光容量建模与投资口径维度归属裁定（P-INFRA-1 W5,审查 F1）

## 裁定

1. **容量指标按设备维度归属,不做比例分摊**:分光容量(潜在/已接/可扩户数)是分光器设备的物理事实,
   odn_device 无网格维度(导入域设备连城市都无,000209 裁定不猜填),因此容量**只进设备视图
   (/odn/split-capacity)与城市行(城市域设备 prv/city 非空者)与全网汇总,不进网格行**;
   网格行硬摊容量会产出假户数(一个 1:64 分光器的容量摊到三个网格各 21 户,物理上不存在)。
   顺序五 W3 收口(导入链回写 grid/facility)接通数据面后,容量入网格行另行裁定,本期不做。
2. **项目级总额(预算/材料成本)按明细金额占比分摊,行级金额一律按行级维度直归**:已结算成本
   (W2 既有)逐明细行自带 facility_code,直归网格不加比例;预算(budget_amount)与材料出库合计
   是项目级总额,无行级网格维度,按「网格内明细金额÷项目有网格归属明细合计」占比分摊;
   零归属明细的项目显式「未登记」不硬摊。即:**有维度用维度,无维度按比例,无比例不硬摊**。
3. **材料成本与结算人工成本分列,禁止混算**:materialCost 只计 CONFIRMED 出库单,资产单价经
   采购价链(assets.batch_id→procurement_receipts→procurement_order_items)取同单同料 id 最小
   一行;无采购价链的资产不计额;settledCost 口径不变(SETTLED 结算单明细金额)。
4. **回写建模=独立显式端点,导入不自动触发**:POST /odn/resource-chains/backfill-split 幂等全量
   重建 odn_device_split_capacity(事务 DELETE+INSERT);写操作入审计,失败留 [odn-split-backfill]
   可 grep 日志。显式重建换取可观测/可重放,避免导入路径隐式写第二张表。
5. **户级口径**:一条二级分光端口=一户;潜在户数(home-passed)=Σ二级分光器容量+Σ无二级链的
   一级分光器容量(直达户);已接=Σ已用端口占用(链行端口标签去重,不解析标签格式);
   可扩=潜在−已接;costPerPotential=(规划+材料+已结算)÷潜在户数(审查 F1:每户成本分母不是
   覆盖户数)。**total_split(一级×二级)不参与汇总**——两级容量相加重复计数,仅作链行暂存事实。
6. **odn_port 与容量模型互补不相混**:odn_port(000200)是订单流物理端口状态机
   (IDLE/RESERVED/IN_SERVICE,供预占/装机);容量模型是规划级事实(分光比分母+链行占用)。
   链行端口状态(可用/已使用/已预留/已封锁)与 odn_port 枚举不同域,不强行映射——
   「已封锁」无对应态,映射即猜填。
7. **设备解析:城市域同名唯一优先,导入域兜底**:导入展开(W3)会为链上箱体创建导入域影子
   设备(prv_code IS NULL),若解析导入域优先,城市容量列永远死列;操作员在城市域实名登记的
   箱体才是物理本体,链行指向同一物理体,容量应随其城市维度进城市行。城市域跨城同名
   (>1 行)歧义不建模不猜填;无城市域登记再退导入域影子(只进全网/设备视图)。

## 为什么

- **设备维度 vs 比例分摊的取舍**:W2 遗留问题是「成本/指标如何落到网格」。物理事实
  (容量)比例摊=造假数据;财务事实(项目级总额)按明细金额占比摊=可解释的会计分摊。
  两者必须区分,故合并为一条总裁定:维度归属优先,比例分摊仅限无行级维度的财务总额。
- **容量物化成表而非纯 SQL 聚合**:链行是 append-only 导入暂存,容量是设备当前事实;
  物化后容量有独立生命周期(后续可在设备上手工修正,链行不改),巡检/断言有单一权威行。
  代价是需要显式重建端点,幂等+审计+日志兜底。
- **MAX(ratio) 消解不一致链行**:同一分光器多行分光比不一致是模板填报错误(导入校验只拦
  单行 total=一级×二级,拦不住跨行不一致);取 MAX 是「容量=物理上限」的自然解释,
  跨行不一致由巡检/人工核对,不在回写里阻塞。

## 放弃了什么

- **容量进网格行**:换取不造假;代价是网格视图暂无潜在户数列(城市视图有),W3 收口后补。
- **解析端口标签物化 odn_port 行**:换取不猜填;代价是容量占用粒度止于「去重计数」,
  无法回答「具体哪个端口空闲」(那是订单流 odn_port 的职责)。
- **导入自动回写**:换取导入路径零隐式副作用;代价是新导入数据需手动(或运维脚本)触发
  一次回写才有容量视图,验收脚本显式覆盖此链路。
- **总 split 口径入汇总**:total_split 只留在链行(1.5.12 暂存),两级容量相加会重复计数,
  户级口径只用「单级端口容量」直接相加。
