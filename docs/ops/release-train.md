# 发布列车规范（稳定版 1.0 起）

> 版本 V1.0｜适用：102 生产环境的所有后端/Admin/端侧发布。
> 目标：变更可评审、可灰度、可回滚、发布后有验证与复盘闭环。

## 1. 版本号规则

- 格式 `MAJOR.MINOR.PATCH`（SemVer）：1.0 为首个生产稳定版。
- 后端、admin web、openapi 契约（`api/openapi/*.yaml`）三者在发布说明中同列版本。
- 迁移号（`migrations/000NNN`）与发布版本在发布说明中互相引用，保证可追溯。

## 2. 发车前门禁（全部绿才发车）

1. `make check`（含 check-contract-sync：契约同步 + 迁移撞号拦截）
2. 三端测试套件（Go test / web test）
3. 契约对账无新增红项（`docs/ops/contract-audit-q4.md` 台账）
4. SLO 错误预算未耗尽（见 `slo.md` §4；耗尽 50% 降速，100% 冻结）
5. 发布说明（changelog）就绪：变更列表 + 迁移列表 + 回滚步骤

## 3. 发布流程（列车时刻）

| 阶段 | 动作 | 责任 | 时限 |
|:-----|:-----|:-----|:-----|
| 候审 | feature 分支过门禁，合并入 main（worktree 协议） | 开发 | 当天 |
| 验证 | main 在隔离环境跑全量回归 + 冒烟 | 开发+审核 | 合并后 1 天内 |
| 灰度 | 102 环境按流量比例放量（见 §4） | 运维 | 逐级观察 ≥30min |
| 全量 | 灰度指标达标后全量 | 运维 | — |
| 复盘 | 发布后 48h 内出验证报告；异常走 postmortem | 发布负责人 | 48h |

## 4. 灰度策略

- 后端单体按「实例」灰度：先 1 台承载观察，核心 SLI（S1/S2/S3）无劣化再扩。
- Admin web 按「用户组」灰度：先内部账号（admin/reviewer）验证，再放开。
- 端侧（user/worker app）按构建渠道灰度：内部测试包 → 灰度包 → 全量包（沿用 `build-install-*-android.sh`）。
- 每级灰度观察 ≥30min，比对 `/metrics` 的 S1/S2/S3 与发布前基线。

## 5. 回滚

### 触发条件（任一即回滚）

- S1 可用性跌破 99%（5min 窗口）或 S3 认证成功率跌破 99%
- 核心链路（下单/派单/扫码绑定）冒烟失败
- 数据损坏风险（迁移导致，见 §6）

### 步骤

1. 回滚二进制/镜像到上一版本（部署产物按版本保留 ≥3 个）
2. **迁移不自动回滚**：`.down.sql` 仅在演练环境执行；生产迁移回滚必须单独评审（down 脚本可能丢数据）
3. 回滚后重跑冒烟 + 确认 SLI 恢复基线
4. 24h 内补记 postmortem（`docs/postmortem/000N-*`，随修复提交）

## 6. 迁移纪律（发布列车子集）

- 每个发布包含的迁移必须先在隔离副本演练（见 `dr-drill.md`），记录耗时与锁影响。
- 破坏性迁移（删列/改类型）拆两列车：先兼容发布（双写/双读），后清理发布。

## 7. 发布后验证清单（每列车必做）

- [ ] `/healthz` 200，`/metrics` 可采
- [ ] 三端冒烟：admin 登录 + 列表页；user 下单；worker 扫码
- [ ] 核心接口抽样比对响应结构（契约不漂移）
- [ ] SLO 看板无新增红项，观察 24h
- [ ] changelog 与发布产物版本一致
